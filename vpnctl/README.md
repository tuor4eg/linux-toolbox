# vpnctl

`vpnctl` удерживает рабочий OpenVPN достижимым, когда общий трафик уходит в Outline или Hiddify через policy routing.

Он делает две разные вещи и только для профилей из `/etc/vpnctl.json`:

1. Если до IPv4-сервера OpenVPN в таблице `main` лежит отдельный маршрут `/32` через обычный шлюз, удаляет этот маршрут, чтобы сервер пошёл через уже работающий прокси. Свой маршрут через прокси утилита не добавляет. Если после удаления трафик к серверу через прокси не пошёл, она возвращает прежний `/32`.
2. Для сетей из `expected_networks` активного профиля ставит правило priority `810`: `from all to СЕТЬ lookup main`. В `main` при этом должен лежать маршрут этой сети через интерфейс `tunN` рабочего OpenVPN. Так сеть офиса не уходит в таблицу прокси.

Встроенных профилей, адресов и UUID в программе из репозитория нет. Пока нет `/etc/vpnctl.json`, любая команда завершается ошибкой и маршруты не меняет: `Отсутствует /etc/vpnctl.json. Настройте рабочие VPN перед использованием.`

Общая установка: [INSTALLATION.md](../INSTALLATION.md). Восстановление компьютера: [docs/recovery.md](../docs/recovery.md). Исключения в другую сторону делает [bypass](../bypass/README.md). Журнал наблюдений: [work-vpn-audit](../work-vpn-audit/README.md).

## Что делает

Профиль — это уже существующее подключение NetworkManager типа `vpn`. Утилита не создаёт OpenVPN-конфиг, не читает его файлы и не хранит пароли. Адрес сервера она либо берёт из поля `endpoint`, либо ищет в командной строке процесса `/openvpn` аргумент `--remote`, и только если это IPv4. Строка UUID профиля должна встречаться в аргументах этого процесса.

Активность определяется так: `nmcli -t -f UUID,TYPE connection show --active`, строки с типом `vpn`. Подключение не через NetworkManager, WireGuard и другие типы `nmcli` не считаются профилем. Если `nmcli` не найден, команда завершается ошибкой `nmcli не найден`. Если `nmcli` завершился с ненулевым кодом, ошибка начинается с `nmcli:`. В обоих случаях профили не помечаются отключёнными и `apply` до маршрутов не доходит. Пустой успешный ответ `nmcli` по-прежнему означает, что активных VPN нет.

Прокси считается включённым, если выполнено одно из двух, в таком порядке:

- В таблице `2022` есть default, его интерфейс существует, имя начинается с `tun`, и маршрут до `1.1.1.1` идёт через тот же интерфейс. Это ветка Hiddify.
- В таблице `7113` есть default, его интерфейс существует, в имени есть `outline`, и маршрут до `1.1.1.1` идёт через тот же интерфейс. Это ветка Outline.

Если `1.1.1.1` у вас направлен отдельно от остального трафика прокси, определение может не сработать. Пока прокси не определён, `apply` пишет, что маршруты к серверам не трогает. Правила сетей, которые утилита раньше записала в свой список, в этом состоянии она как раз снимает: без прокси они не нужны.

Priority `810` фиксирован, в конфиге его нет. Он задуман ниже пользовательских правил вроде `800` у [bypass](../bypass/README.md) и выше типичных правил Outline/Hiddify. Меньшее число ядро смотрит раньше. Исключение `bypass` на конкретный адрес внутри рабочей сети перебьёт правило `810` и уведёт этот адрес в обычный шлюз. Адрес сервера OpenVPN и сети из `expected_networks` в `bypass` не добавляют. Их место — `protected_endpoints` и `protected_networks` политики `bypass`.

Правила `ip rule` после перезагрузки сами не восстанавливаются. Их заново ставит `apply`, вручную или по таймеру. Список своих сетей хранится в `/run/vpnctl-managed-rules.json` и после перезагрузки тоже пуст. Чужое правило с тем же priority утилита не присваивает и поэтому позже само не удалит.

## Установка

```bash
cd ~/pets/linux-toolbox
./install.sh check vpnctl
./install.sh install vpnctl
```

Программа копируется в `/usr/local/bin/vpnctl`. Рядом в `/etc/systemd/system/` кладутся [vpnctl.service](systemd/vpnctl.service) и [vpnctl.timer](systemd/vpnctl.timer). Таймер при этом не включается. Конфиг не создаётся. Если `/etc/vpnctl.json` ещё нет, установка останавливается и файл не записывает.

Нужны Python 3.10 или новее (так указано в самой программе), `ip`, `nmcli`, `sudo`. Для команды `check` ещё нужен `ping`. Установщик проверяет наличие `ip` и `nmcli` только предупреждением.

Повторная установка с заменой программы и unit-файлов:

```bash
./install.sh install vpnctl --replace
```

Старые файлы копируются в каталог `/var/backups/linux-toolbox-*`. `/etc/vpnctl.json` не входит в эту копию и не изменяется. Если таймер уже был включён, после `daemon-reload` следующий тик выполнит уже новую программу. Перед заменой его лучше остановить, посмотреть `--dry-run` и включить снова. Команды ниже, в разделе обновления.

`--enable-timer` включает таймер сразу, без сухого прогона. Пока конфиг не проверен, этот флаг не используйте.

## Настройка с нуля

Узнайте UUID подключений NetworkManager. Это диагностика, маршруты не меняются:

```bash
nmcli -t -f NAME,UUID,TYPE connection show
nmcli -t -f NAME,UUID,TYPE connection show --active
```

В конфиг попадает UUID строки с типом `vpn`. Имя профиля в JSON может быть любым коротким словом, на имя в NetworkManager оно не обязано быть похожим. Программа обращается к профилю по этому имени в команде `endpoint`.

Посмотрите, есть ли у процесса OpenVPN аргумент `--remote` с IPv4:

```bash
ps -eo args | grep '[o]penvpn'
```

Если в командной строке `--remote` нет или там DNS-имя, автоматическое определение не сработает. Для `status` DNS-имя в `--remote` даёт ошибку `OpenVPN использует DNS-имя сервера; задайте IPv4 вручную через endpoint`. Для такого профиля запишите IPv4 в поле `endpoint`.

Скопируйте пример и отредактируйте. Пример: [config.example.json](config.example.json).

```bash
sudo install -m 600 -o root -g root \
  vpnctl/config.example.json /etc/vpnctl.json
sudoedit /etc/vpnctl.json
```

```json
{
  "profiles": {
    "work": {
      "uuid": "00000000-0000-0000-0000-000000000000",
      "endpoint": "auto",
      "expected_networks": [
        "10.0.0.0/24"
      ]
    }
  }
}
```

Нулевой UUID из примера замените на UUID из `nmcli`. Второй профиль добавляется таким же объектом рядом с `work`.

| Поле | Обязательность | Смысл |
| --- | --- | --- |
| `uuid` | да | UUID подключения NetworkManager. Без него `status` и `apply` падают с ошибкой ключа. |
| `endpoint` | нет, по умолчанию смысл как у `auto` | `auto` или IPv4-адрес сервера OpenVPN. Другая строка отклоняется. |
| `expected_networks` | нет | Список префиксов, для которых нужно правило `lookup main`. Префикс сравнивается с маршрутом в таблице `main` целиком: `10.0.0.0/24` в конфиге не совпадёт с маршрутом `10.0.0.0/16`. Лишние биты хоста при разборе отбрасываются. |

Корень файла — объект с ключом `profiles`. Другие ключи верхнего уровня команда `endpoint` при сохранении не записывает обратно. Лишние поля внутри профиля сохраняются.

`expected_networks` описывает сети, маршрут которых OpenVPN уже поставил в `main` через интерфейс с именем `tun` и номером, например `tun0`. Маршрут через интерфейс с другим именем правило не получит. При пересечении сетей у нескольких профилей в ядре остаётся тот маршрут, который реально лежит в `main`; порядок профилей в JSON его не переопределяет.

Пока таймер выключен, последовательность такая. `status` и `--dry-run` маршруты не меняют. `apply` без флага уже может удалить `/32` и добавить правила.

```bash
sudo vpnctl status
sudo vpnctl apply --dry-run
sudo vpnctl apply
```

## Команды

| Команда | Что делает | Меняет систему |
| --- | --- | --- |
| `vpnctl status` | Печатает, какой прокси найден, и по каждому профилю: подключён ли UUID, endpoint и `ip route get` до сервера и до адреса сети. | нет |
| `vpnctl check АДРЕС` | Печатает маршрут до IPv4 и выполняет `ping -n -c 3 -W 2`. Если `ping` запустился, код выхода совпадает с его кодом. Если программы `ping` нет, будет `Ошибка:` и код 1. Имя хоста не резолвится. | нет, только ICMP |
| `vpnctl apply --dry-run` | Печатает, какие `ip` были бы выполнены. В ядро и в файл состояния не пишет. | нет |
| `vpnctl apply` | Выполняет удаление конфликтующего `/32`, откат этого маршрута при неудаче и синхронизацию правил `810`. | да, маршруты и правила |
| `vpnctl endpoint ПРОФИЛЬ auto` | Записывает в конфиг автоматическое определение. Маршруты не трогает, пока не будет `apply`. | да, только `/etc/vpnctl.json` |
| `vpnctl endpoint ПРОФИЛЬ A.B.C.D` | Записывает фиксированный IPv4 сервера. | да, только конфиг |
| `vpnctl install-timer` | Записывает unit-файлы и сразу включает таймер. | да, systemd |

Неизвестное имя в `endpoint` даёт `Неизвестный профиль`. Запись конфига и любые реальные изменения маршрутов требуют root: `Для сохранения настроек требуется sudo`, `Для изменения маршрута требуется sudo`, `Для изменения сетевых правил требуется sudo`.

Если менять нечего, `apply` может обойтись без root, но при файле `600` прочитать конфиг всё равно может только root. Практический вызов — через `sudo`.

`status` у подключённого профиля с `endpoint: auto` читает командную строку OpenVPN. Если `--remote` отсутствует, endpoint в выводе будет `—`. Если процесс не найден, то же самое.

Текст `apply` по каждому профилю — одна из фраз:

- `OpenVPN отключён — пропуск`
- `не удалось определить IP OpenVPN-сервера`
- `Hiddify/Outline не обнаружен — маршруты не трогаем`
- `OK, АДРЕС уже идёт через hiddify (интерфейс)` или `outline`
- `АДРЕС не идёт через прокси; отдельного /32 маршрута нет — без изменений`
- `маршрут /32 через VPN — автоматическое удаление запрещено` (интерфейс маршрута — это прокси или имя начинается с `tun`)
- `исправлено — АДРЕС теперь через …`
- `прокси-маршрут не появился — прямой маршрут восстановлен`
- в `--dry-run`: `удалили бы ip -4 route del …; затем проверили бы маршрут через …`

Следом идёт строка про сети. В боевом `apply` это `Сети: N через рабочий VPN, правил под управлением vpnctl: M`. В `--dry-run` это `Сети: без изменений` либо одна строка с командами `ip -4 rule add` и `ip -4 rule del`.

Удаляется только точный маршрут хоста в таблице `main`, у которого есть и gateway, и интерфейс. Маршрут `/32` без gateway остаётся на месте, и текст будет про отсутствие отдельного `/32`. Если таких маршрутов с gateway несколько, берётся первый, который вернул `ip -j`. Маршрут через `tun` или через интерфейс найденного прокси не удаляется.

Если после удаления сервер не пошёл через прокси, команда возвращает маршрут, включая `metric`, если он был. Если вернуть его не удалось, программа останавливается с `маршрут НЕ восстановлен` и код 1. В этом состоянии прямой `/32` может уже отсутствовать. Смотрите `ip -4 route show table main` и при необходимости верните маршрут вручную теми gateway и интерфейсом, которые были в тексте ошибки до сбоя. Это уже ручное изменение маршрутизации.

Правила добавляются только для сетей, которых ещё нет в выводе `ip rule` и не было в файле состояния. Пропавшее своё правило добавляется снова. Лишнее своё правило удаляется. Существующее правило, которого утилита не создавала в этом сеансе загрузки, она не забирает себе.

### Сухой прогон и реальный apply

`--dry-run` вызывает те же чтения `nmcli` и `ip route get`, что и боевая команда, и на этом заканчивается. Он не создаёт `/run/vpnctl-managed-rules.json` и не является бронированием маршрута. Между сухим прогоном и `apply` вывод `ip rule` может измениться.

Реальный `apply` может удалить `/32` и тут же вернуть его, если прокси-маршрут не появился. Правила `810` он добавляет и удаляет по текущему списку своих сетей. Пока прокси не виден, желаемый список сетей пуст, и ранее записанные свои правила снимаются.

Таймер вызывает именно `apply`, без `--dry-run`.

### Таймер

Unit-файлы репозитория:

- `vpnctl.service` — `Type=oneshot`, `ExecStart=/usr/local/bin/vpnctl apply`. Зависимости от сети в unit нет. Пользователь не задан, служба идёт от root.
- `vpnctl.timer` — `OnBootSec=15s`, `OnUnitActiveSec=15s`, `AccuracySec=2s`. Следующий запуск примерно через 15 секунд после старта предыдущего, с допуском около двух секунд. Первый — через 15 секунд после загрузки.

Включение после сухого прогона. Это уже меняет состав служб и с первого срабатывания может менять маршруты:

```bash
sudo systemctl enable --now vpnctl.timer
systemctl list-timers vpnctl.timer
```

Один проход без включения таймера выполняет тот же боевой `apply` и может менять маршруты:

```bash
sudo systemctl start vpnctl.service
journalctl -u vpnctl.service -n 40 --no-pager
```

Команда `sudo vpnctl install-timer` делает другое. Она требует root и уже установленный `/usr/local/bin/vpnctl`, записывает оба unit-файла текстом, который вшит в программу, выполняет `daemon-reload` и сразу `systemctl enable --now vpnctl.timer`. Сейчас этот текст совпадает с файлами в `vpnctl/systemd/`. Отдельного сухого прогона у этой команды нет. Если когда-нибудь файлы в репозитории и текст в программе разойдутся, `install-timer` запишет вшитую копию, а `./install.sh` — копию из каталога `systemd/`. Для обычной установки достаточно установщика репозитория и явного `systemctl enable`.

Остановка автоматических правок:

```bash
sudo systemctl disable --now vpnctl.timer
```

Уже добавленные правила `810` при остановке таймера сами не исчезают. Они исчезнут при перезагрузке или при следующем `apply`, если прокси не обнаружен и сети ещё числятся в `/run/vpnctl-managed-rules.json`.

## Примеры

Диагностика:

```bash
sudo vpnctl status
sudo vpnctl apply --dry-run
sudo vpnctl check 203.0.113.10
ip -4 rule show
ip -4 route show table 2022
ip -4 route show table 7113
```

Зафиксировать адрес сервера и вернуть автоопределение. Меняется только JSON:

```bash
sudo vpnctl endpoint work 198.51.100.20
sudo vpnctl endpoint work auto
```

Применить пойманные отличия. Меняет маршруты, если сухой прогон показал команды `ip`:

```bash
sudo vpnctl apply
```

Посмотреть, что таймер уже натворил, не останавливая его:

```bash
systemctl status vpnctl.timer
journalctl -u vpnctl.service -n 40 --no-pager
```

## Файлы

| Путь | Содержание |
| --- | --- |
| `/usr/local/bin/vpnctl` | Программа. |
| `/etc/vpnctl.json` | Профили. Создаётся вами, режим лучше выставить `600`. В Git не класть: внутри UUID и рабочие префиксы. |
| `/run/vpnctl-managed-rules.json` | JSON-список сетей, правила которых утилита считает своими. Живёт до перезагрузки. |
| `/etc/systemd/system/vpnctl.service` | Разовый `apply`. |
| `/etc/systemd/system/vpnctl.timer` | Повтор примерно каждые 15 секунд. |
| `/var/backups/linux-toolbox-*` | Копии программы и unit-файлов после установки или `--replace`. Конфига там нет. |

Файл примера в репозитории — [config.example.json](config.example.json).

`work-vpn-audit` читает тот же `/etc/vpnctl.json` и маршруты не меняет.

## Права и sudo

| Действие | sudo |
| --- | --- |
| `status`, `check`, `apply --dry-run` | Практически да: конфиг `600`. Сами команды маршруты не пишут. |
| `apply` | Да, как только нужно выполнить `ip`. |
| `endpoint` | Да, запись в `/etc`. |
| `install-timer`, `systemctl enable` | Да. |

Чтение OpenVPN ограничено командной строкой процесса. Файлы соединений NetworkManager утилита не открывает.

## Проверка

Маршруты не меняются:

```bash
sudo vpnctl status
sudo vpnctl apply --dry-run
ip -4 rule show | grep 810 || true
ip -4 route get 198.51.100.20
```

Адрес во второй паре команд замените на endpoint из `status`.

Ожидание при рабочей схеме: `status` показывает `hiddify` или `outline` и имя интерфейса; у подключённого профиля endpoint не `—`; `route get` до сервера идёт через интерфейс прокси; для каждой сети из `expected_networks` маршрут идёт через `tunN`. После реального `apply` в `ip -4 rule show` есть `810: from all to 10.0.0.0/24 lookup main` с вашим префиксом. Сухой прогон эту строку только предсказывает.

`check` дополнительно шлёт три ICMP-запроса. Ненулевой код означает, что `ping` не получил ответ или не запустился. На маршруты это не влияет.

Перед включением таймера сухой прогон должен печатать либо `без изменений` и `OK`, либо ровно те `ip rule`, которые вы ожидаете. Неожиданный `route del` — повод не включать таймер и разобрать, чей это `/32`.

## Обновление

Если сейчас установлена более старая копия программы, в которой профили были зашиты в сам файл, после перехода на версию из репозитория источником остаётся только `/etc/vpnctl.json`. Убедитесь, что в файле есть все нужные профили, до `--replace`. Содержимое чужого бинарника в этот справочник не копируется.

Остановить таймер, обновить файл, ещё раз посмотреть план и включить таймер:

```bash
cd ~/pets/linux-toolbox
git pull
./install.sh check vpnctl
sudo systemctl disable --now vpnctl.timer
./install.sh install vpnctl --replace
sudo vpnctl status
sudo vpnctl apply --dry-run
sudo systemctl enable --now vpnctl.timer
```

`disable` перестаёт запускать автоматический `apply`. Уже стоящие правила до перезагрузки или следующего `apply` сохраняются. Конфиг установщик не трогает.

## Отключение и удаление

Остановить периодические изменения:

```bash
sudo systemctl disable --now vpnctl.timer
```

Самый прямой способ убрать правила `810` из ядра — перезагрузка: `ip rule` на диске не хранится. Файл `/run/vpnctl-managed-rules.json` при этом тоже пропадёт.

Без перезагрузки свои правила снимает `sudo vpnctl apply` в момент, когда прокси уже не обнаружен, а файл состояния ещё перечисляет эти сети. Выключение Outline/Hiddify само меняет маршрутизацию всей системы. Имеет смысл только если вы и так их останавливаете. Чужие правила priority `810` этот вызов не удалит.

Посмотреть, что ещё осталось, можно без изменений:

```bash
ip -4 rule show
```

Удалять конкретную строку вручную стоит только если вы узнали в ней сеть из своего `expected_networks`. Пример формы команды, адреса подставьте свои. Это меняет маршрутизацию:

```bash
sudo ip -4 rule del priority 810 to 10.0.0.0/24 lookup main
```

Маршрут `/32`, который `apply` когда-то удалил, при удалении утилиты сам не возвращается.

Снять unit-файлы и программу, конфиг оставить для следующей установки:

```bash
sudo systemctl disable --now vpnctl.timer
sudo rm -f /etc/systemd/system/vpnctl.service /etc/systemd/system/vpnctl.timer
sudo systemctl daemon-reload
sudo rm -f /usr/local/bin/vpnctl
```

`/etc/vpnctl.json` удаляйте отдельно, если он больше не нужен. Для переустановки Ubuntu его как раз сохраняют: [docs/recovery.md](../docs/recovery.md).

## Ошибки и диагностика

| Что видно | Что проверить |
| --- | --- |
| `Отсутствует /etc/vpnctl.json` | Файл не скопирован. Команды маршруты не меняли. |
| `Неизвестный профиль` | Имя в `endpoint` не совпало с ключом в `profiles`. |
| `nmcli не найден` или `nmcli: …` | Команды `nmcli` нет либо она завершилась с ошибкой. Это не список отключённых профилей. Маршруты не менялись. |
| Все профили «отключён» | `nmcli` отработал успешно, но UUID нет среди активных подключений типа `vpn`. `nmcli connection show --active`. |
| `не удалось определить IP` или прочерк endpoint | В командной строке OpenVPN нет `--remote` с IPv4. Задайте адрес через `vpnctl endpoint`. |
| `OpenVPN использует DNS-имя сервера` | В `--remote` имя, не IPv4. `status` на этом останавливается. Запишите адрес вручную. |
| `Hiddify/Outline не обнаружен` | Нет подходящего default в таблице `2022` или `7113`, либо путь к `1.1.1.1` идёт через другой интерфейс. `ip -4 route show table 2022`, `table 7113`, `ip -4 route get 1.1.1.1`. Маршруты серверов при этом не меняются. Свои старые правила сетей боевой `apply` снимет. |
| `маршруты не трогаем` | Тот же случай: прокси не найден. |
| `отдельного /32 маршрута нет` | Сервер и так не через прокси, но удалять нечего. Либо маршрут без gateway. Смотрите `ip -4 route get АДРЕС`. |
| `автоматическое удаление запрещено` | Найденный `/32` идёт через `tun` или через интерфейс прокси. Утилита его бережёт. |
| `прямой маршрут восстановлен` | Удаление `/32` не привело трафик в прокси, маршрут возвращён. Разберите `ip rule` и таблицы `2022`/`7113`. |
| `маршрут НЕ восстановлен` | Откат `/32` не выполнился. Сверьте таблицу `main` с тем, что печаталось до ошибки. |
| Таймер есть, а сети после загрузки не сразу открываются | Первый запуск через 15 секунд и без `network-online.target`. Посмотрите `journalctl -u vpnctl.service`. |
| `bypass` уводит рабочий адрес напрямую | У `bypass` priority `800`, он раньше `810`. Уберите этот адрес из исключений `bypass` и внесите его в политику защиты. |

Журнал службы читается так и систему не меняет:

```bash
journalctl -u vpnctl.service -n 80 --no-pager
systemctl list-timers vpnctl.timer
```

## Ограничения и безопасность

- Только IPv4 и только подключения NetworkManager типа `vpn`.
- Прокси распознаётся по таблицам `2022` и `7113` и по маршруту до `1.1.1.1`. Другая схема Outline/Hiddify может остаться незамеченной.
- Утилита не создаёт маршрут через прокси. Она убирает мешающий прямой `/32` и ждёт, что policy routing прокси уже настроен.
- Не читает конфиги OpenVPN и не обходит пароль. Если сервер не попал в командную строку как IPv4, его нужно вписать самому.
- Не управляет исключениями `bypass` и не видит его реестр.
- Сухой прогон ничего не закрепляет.
- Таймер каждые ~15 секунд выполняет боевой `apply`. Ошибочная сеть в `expected_networks` будет регулярно получать правило `lookup main`.
- Свои правила помнит только до перезагрузки. Чужие правила с priority `810` не удаляет.
- `/etc/vpnctl.json` содержит UUID и рабочие префиксы. Режим `600`, в Git не коммитить.
- Откат `/32` — одна попытка вернуть тот же gateway, интерфейс и metric. Отдельного журнала прежних маршрутов на диске нет.
