# work-vpn-audit

`work-vpn-audit` ведёт локальный журнал рабочих VPN. Каждая запись отвечает на два вопроса: было ли подключение NetworkManager с UUID из `/etc/vpnctl.json` активно и какой IPv4 ответил пробный запрос с того интерфейса, через который в этот момент шёл маршрут до сервера OpenVPN.

Утилита не меняет маршруты, правила, `vpnctl` и подключения. Единственная запись на диск — её собственная база SQLite. Программу `vpnctl` ставить не обязательно, но файл `/etc/vpnctl.json` нужен: из него берутся имена профилей, UUID и поле `endpoint`.

Наблюдаемый IP — ответ `https://api.ipify.org` на запрос, привязанный к выбранному интерфейсу. Это не адрес, который сообщил сервер OpenVPN, и не строка из серверного журнала. Адрес клиента внутри рабочего туннеля утилита тоже не читает.

Общая установка: [INSTALLATION.md](../INSTALLATION.md). Восстановление компьютера и сохранение истории: [docs/recovery.md](../docs/recovery.md). Откуда берётся конфиг: [vpnctl/README.md](../vpnctl/README.md).

## Что делает

Для каждого профиля с непустым `uuid`:

- UUID нет среди активных подключений NetworkManager типа `vpn`. В базу пишется отключение: `connected = 0`, канал `none`, статус `disconnected`. Запрос наружу не выполняется.
- Профиль активен, а IPv4 сервера узнать нельзя. Пишется `unverified` с текстом `cannot determine OpenVPN endpoint`. Запрос наружу не выполняется. Так бывает, если `endpoint` не `auto` и не является IPv4, либо в командной строке OpenVPN нет `--remote` с IPv4. DNS-имя в `--remote` сюда тоже попадает: в отличие от `vpnctl status`, аудит в этом случае не падает, а пишет непроверенную строку.
- Профиль активен и IPv4 сервера известен. `ip -4 route get` показывает интерфейс пути к этому серверу. К интерфейсу привязывается `curl -4` на `https://api.ipify.org`. Успех даёт `probe_ok` и адрес. Сбой curl, пустой интерфейс или не-IPv4 ответ дают `probe_failed` и короткий текст причины. Строка всё равно записывается, признак подключения остаётся `1`.

Откуда берётся адрес сервера: при `endpoint: auto` или при отсутствии поля — аргумент `--remote` процесса, путь которого заканчивается на `/openvpn`, если в командной строке есть UUID и значение `--remote` является IPv4. Иначе используется буквальный IPv4 из конфига. Файлы OpenVPN не читаются.

Класс канала — это интерфейс пути к серверу, не интерфейс самого рабочего туннеля:

| Имя интерфейса | `channel` |
| --- | --- |
| начинается с `outline-tun` | `outline` |
| начинается с `tun` или `hiddify` | `hiddify-or-other-tun` |
| любое другое | `direct-or-other` |
| интерфейса нет | `unknown` |

`hiddify-or-other-tun` поэтому означает «путь к серверу идёт через какой-то tun или через интерфейс с именем на `hiddify`», а не «это точно Hiddify, а не рабочий OpenVPN». Если маршрут до сервера смотрит в `wlan0` или `eth0`, канал будет `direct-or-other`: рабочий VPN может быть включён, но до его сервера система доходит мимо прокси. Пробный IP в этом случае — внешний адрес этого прямого интерфейса.

Пока путь к серверу идёт через интерфейс Outline, пробный IP — внешний адрес этого интерфейса. Часто он совпадает с тем, что увидел бы сервер OpenVPN, но утилита сверки с сервером не делает.

Один проход ходит в ipify не больше одного раза на интерфейс, даже если несколько профилей делят этот путь. Сервис в коде фиксирован, сменить URL флагом нельзя. Для дочерних процессов очищаются `http_proxy`, `https_proxy`, `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` и `all_proxy`, у curl дополнительно `--noproxy '*'`. Привязка задаётся как `--interface if!ИМЯ`: если встать на этот интерфейс не удалось, curl не переключается на другой, и строка получает `probe_failed`. Успешный запрос всё равно уходит на api.ipify.org, и этому сервису виден исходящий адрес.

Если `nmcli` или чтение конфига завершились ошибкой, в базу ничего не пишется. Ложные строки «VPN выключен» из-за сломанного `nmcli` не создаются.

Время в базе — UTC в виде `2026-11-23T18:40:00+00:00`. В `history` оно показывается в локальном часовом поясе.

Поля строки:

| Поле | Смысл |
| --- | --- |
| `observed_at` | Время сбора, UTC. |
| `profile` | Имя из `/etc/vpnctl.json`. |
| `uuid` | UUID NetworkManager. |
| `connected` | `1` или `0`. |
| `endpoint` | IPv4 сервера или пусто. |
| `interface` | Интерфейс маршрута до сервера или пусто. |
| `channel` | Класс из таблицы выше, `none` у отключения. |
| `public_ip` | Ответ пробы или пусто. |
| `probe_status` | `disconnected`, `unverified`, `probe_ok`, `probe_failed`. |
| `detail` | Текст ошибки или пустая строка. Успешный запрос и обычное отключение оставляют его пустым. |

Сети `expected_networks` в журнал не попадают и отдельно не опрашиваются.

## Установка

Сначала должен существовать `/etc/vpnctl.json`. Как его собрать: [vpnctl/README.md](../vpnctl/README.md).

```bash
cd ~/pets/linux-toolbox
./install.sh check work-vpn-audit
./install.sh install work-vpn-audit
```

Программа копируется в `/usr/local/bin/work-vpn-audit`. В `/etc/systemd/system/` кладутся [work-vpn-audit.service](systemd/work-vpn-audit.service) и [work-vpn-audit.timer](systemd/work-vpn-audit.timer). Таймер не включается. База не создаётся, пока не выполнится успешный `audit`.

Нужны Python 3 со стандартным модулем `sqlite3`, `nmcli`, `ip`, `curl`, `sudo`. Установщик требует `python3`, `nmcli`, `ip` и `curl`: без любой из них `check` завершается с кодом 1. Установка также требует уже существующий `/etc/vpnctl.json` и этот файл не создаёт и не перезаписывает. Если `curl` исчезнет уже после установки, `audit` запишет `probe_failed`.

Повторная установка:

```bash
./install.sh install work-vpn-audit --replace
```

База и `/etc/vpnctl.json` не копируются в `/var/backups` и не изменяются. Если таймер уже включён, после `daemon-reload` следующий запуск пойдёт новым файлом. На маршруты это не влияет.

`--enable-timer` включает таймер сразу. Имеет смысл сначала один раз вызвать `audit` руками и посмотреть `history`.

## Настройка с нуля

Отдельного конфига у аудита нет. Профили правятся в `/etc/vpnctl.json`. Профиль без `uuid` пропускается. Если не осталось ни одного профиля с UUID, `audit` завершается ошибкой `ни одного VPN-профиля в конфигурации` и базу не пополняет. Пустой объект `profiles` даёт `в /etc/vpnctl.json нет profiles`.

Ручной проход и просмотр. `audit` требует root даже когда файл конфига читается без него:

```bash
sudo work-vpn-audit audit
sudo work-vpn-audit history
```

Когда строки выглядят правдоподобно, включите таймер. Это меняет состав служб, маршруты не меняет:

```bash
sudo systemctl enable --now work-vpn-audit.timer
systemctl list-timers work-vpn-audit.timer
```

Служба: `Type=oneshot`, `ExecStart=/usr/local/bin/work-vpn-audit audit`, `TimeoutStartSec=40`, `After=NetworkManager.service`. Ожидания `network-online.target` нет, пользователь в unit не задан, служба идёт от root.

Таймер: первый запуск через `OnBootSec=30s` после загрузки, дальше через `OnUnitInactiveSec=60s` после того, как предыдущая служба стала неактивной. С учётом времени самого прохода это примерно раз в минуту. `AccuracySec=5s` позволяет systemd сдвинуть запуск на несколько секунд. Своего `install-timer` у программы нет, в отличие от `vpnctl`.

Ранний запуск после загрузки может поймать ещё не поднятую сеть. Если VPN уже числится активным, а curl не достучался, в базе будет `probe_failed`, а не пропуск. Если NetworkManager не ответил, проход завершится ошибкой и эта попытка в базу не попадёт.

Обрыв по `TimeoutStartSec` может не оставить строку этого прохода. Следующий тик попробует снова.

## Команды

| Команда | Аргументы | Что делает |
| --- | --- | --- |
| `sudo work-vpn-audit audit` | нет | Один сбор и запись. |
| `work-vpn-audit history` | см. ниже | Читает базу, ничего не пишет. |

Аргументы `history`:

| Флаг | По умолчанию | Смысл |
| --- | --- | --- |
| `--days N` | `7` | Нижняя граница окна: сейчас минус N суток, сравнение по UTC-строке времени. N — целое больше нуля. |
| `--ip A.B.C.D` | нет фильтра | Точное совпадение с наблюдаемым `public_ip`. Не endpoint и не префикс. Только IPv4. |
| `--changes` | выключен | Оставляет строку, если отпечаток профиля изменился внутри этого окна. |
| `--limit N` | `200` | После фильтра по IP и по изменениям оставляет N последних строк. N больше нуля. |

Других флагов нет. Отбора по имени профиля нет. Произвольных дат «с … по …» нет, только последние N суток.

Отпечаток для `--changes`: `connected`, endpoint, интерфейс, канал, наблюдаемый IP и `probe_status`. Текст `detail` в сравнение не входит: новая формулировка той же ошибки curl отдельной строкой не станет. Сначала отбрасываются строки старше `--days` и, если указан `--ip`, строки с другим наблюдаемым IP. Затем первая оставшаяся строка каждого профиля показывается всегда, даже если до окна состояние было таким же. Следующая строка того же профиля остаётся, только если отпечаток отличается от предыдущей оставшейся строки.

Порядок печати — от старых к новым среди оставшихся после `--limit` строк. В конце: `Показано N записей; IP — результат локального пробного запроса, не лог рабочего сервера.` Пустая выборка: `Записей нет`. Нет файла базы: `Истории пока нет. Сначала запустите sudo work-vpn-audit audit`.

`--days 0` и `--limit 0` дают `days и limit должны быть положительными`.

Пример строки `audit`:

```text
work: probe_ok; server=198.51.100.20; via=outline (outline-tun0); probe_ip=203.0.113.50
```

Пример строки `history`:

```text
2026-11-23 21:40:00 +0300 | work       | UP   | server=198.51.100.20 | outline/outline-tun0 | IP=203.0.113.50 | probe_ok
```

Отключение выглядит как `DOWN`, `server=—`, `none/—`, `IP=—`, статус `disconnected`.

## Примеры

Один замер и обычный просмотр. `audit` пишет базу. `history` только читает:

```bash
sudo work-vpn-audit audit
sudo work-vpn-audit history
sudo work-vpn-audit history --days 30
sudo work-vpn-audit history --changes
sudo work-vpn-audit history --ip 203.0.113.50
sudo work-vpn-audit history --days 1 --changes --limit 50
```

Только смены канала или IP за неделю, без повторов каждый минутный тик:

```bash
sudo work-vpn-audit history --days 7 --changes --limit 200
```

Журнал службы, без остановки таймера:

```bash
systemctl status work-vpn-audit.timer
journalctl -u work-vpn-audit.service -n 40 --no-pager
```

Число строк в базе. Нужен пакет `sqlite3`. Запрос читающий:

```bash
sudo sqlite3 /var/lib/work-vpn-audit/history.sqlite3 \
  'SELECT COUNT(*) FROM observations;'
```

## Файлы

| Путь | Права | Содержание |
| --- | --- | --- |
| `/usr/local/bin/work-vpn-audit` | `755` | Программа. |
| `/etc/vpnctl.json` | лучше `600` | Чужой для аудита конфиг профилей. Аудит его не переписывает. |
| `/var/lib/work-vpn-audit/` | `700`, root | Каталог базы. |
| `/var/lib/work-vpn-audit/history.sqlite3` | `600`, root | История. В Git не класть. |
| `/etc/systemd/system/work-vpn-audit.service` | `644` | Разовый `audit`. |
| `/etc/systemd/system/work-vpn-audit.timer` | `644` | Периодический запуск. |

Рядом с базой на время записи может появиться журнал SQLite. В репозитории маска `*.sqlite3-*` такие файлы игнорирует. Для резервной копии надёжнее команда `.backup`, а не копирование случайного журнала. Как сохранить историю перед переустановкой Ubuntu: [docs/recovery.md](../docs/recovery.md).

Индексы `observations_lookup` и `observations_ip` создаются самой программой. Отдельная миграция схемы не нужна: таблица создаётся при первом успешном `audit`, если её ещё нет.

## Права и sudo

`audit` без root сразу завершается: `audit требует sudo (конфигурация vpnctl доступна root)`. Так сделано даже если конфиг случайно доступен обычному пользователю.

`history` права не проверяет, но база и каталог принадлежат root и закрыты режимами `600` и `700`. На практике `history` тоже запускают через `sudo`. Иначе SQLite сообщит об отказе в доступе.

Таймер и так работает от root.

## Проверка

После ручного `audit`:

```bash
sudo work-vpn-audit history --days 1 --limit 20
```

Сверьте строку с маршрутом до сервера. Адрес подставьте из колонки `server`. Эта команда маршруты не меняет:

```bash
ip -4 route get 198.51.100.20
```

Интерфейс в `history` должен совпадать с `dev` в выводе `ip`. Если VPN выключен, новая строка после `audit` будет `DOWN` / `disconnected`, без IP.

Включённый таймер виден так:

```bash
systemctl list-timers work-vpn-audit.timer
journalctl -u work-vpn-audit.service -n 20 --no-pager
```

Минутные повторы одного и того же состояния в обычном `history` — норма. Для ленты событий добавьте `--changes`.

## Обновление

```bash
cd ~/pets/linux-toolbox
git pull
./install.sh check work-vpn-audit
./install.sh install work-vpn-audit --replace
```

История остаётся в `/var/lib/work-vpn-audit/history.sqlite3`. Таймер, если был включён, остаётся включённым. Перед заменой можно остановить его, если не хотите прохода посередине копирования файла программы:

```bash
sudo systemctl disable --now work-vpn-audit.timer
./install.sh install work-vpn-audit --replace
sudo systemctl enable --now work-vpn-audit.timer
```

## Отключение и удаление

Остановить опрос:

```bash
sudo systemctl disable --now work-vpn-audit.timer
```

Снять unit-файлы и программу, базу оставить:

```bash
sudo systemctl disable --now work-vpn-audit.timer
sudo rm -f /etc/systemd/system/work-vpn-audit.service /etc/systemd/system/work-vpn-audit.timer
sudo systemctl daemon-reload
sudo rm -f /usr/local/bin/work-vpn-audit
```

Удалять `/var/lib/work-vpn-audit/history.sqlite3` стоит только когда история больше не нужна. `/etc/vpnctl.json` принадлежит ещё и `vpnctl`; эта инструкция его не удаляет.

## Ошибки и диагностика

| Что видно | Что это значит |
| --- | --- |
| `audit требует sudo` | Повторите через `sudo`. База не менялась. |
| `Отсутствует` файл или `Permission denied` на конфиге | Нет `/etc/vpnctl.json` или его нельзя прочитать. Запись в базу не делалась. |
| `в /etc/vpnctl.json нет profiles` | В корне нет непустого объекта `profiles`. |
| `ни одного VPN-профиля в конфигурации` | У всех профилей пустой `uuid`. |
| `nmcli: …` | NetworkManager не ответил. Строка «всё выключено» не записывается. |
| `unverified`, `cannot determine OpenVPN endpoint` | VPN в NetworkManager активен, IPv4 сервера из процесса или из поля `endpoint` не получился. Задайте IPv4 командой `sudo vpnctl endpoint`. |
| `probe_failed` и текст curl | Интерфейс есть, запрос к api.ipify.org не удался: нет маршрута в интернет, нет `curl`, таймаут, чужой ответ. Подключение при этом могло быть `UP`. |
| `probe_failed`, `route has no interface` или текст ошибки `ip` | `ip route get` до сервера не показал интерфейс или завершился с ошибкой. |
| `invalid response from IP probe` | Ответ сервиса не является IPv4. |
| `Истории пока нет` | База ещё не создана. Нужен один успешный `sudo work-vpn-audit audit`. |
| `Записей нет` | База есть, в окне `--days` и с фильтром `--ip` строк не нашлось. |
| `days и limit должны быть положительными` | Передан 0 или отрицательное число. |
| В `history` отказ доступа | Запускайте через `sudo`. |
| Таймер активен, в журнале пусто в первые секунды загрузки | Первый запуск через 30 секунд и только после юнита NetworkManager, не после появления интернета. |
| IP есть, а «через VPN я его не узнаю» | Колонка `IP` — проба с интерфейса пути к серверу. Адрес, назначенный вам внутри OpenVPN, в эту колонку не пишется. |

Пока сеть пропала, а VPN в NetworkManager всё ещё активен, очередной `audit` сохранит `probe_failed` с текстом curl. Когда VPN отключится, следующая строка будет `disconnected` без пробы.

## Ограничения и безопасность

- Маршруты и VPN не изменяются. Ошибка аудита их не чинит и не ломает.
- IP не подтверждён сервером рабочего VPN. Это ответ внешнего HTTPS-сервиса с выбранного интерфейса.
- Только IPv4. Проба всегда идёт на api.ipify.org; каждый успешный замер сообщает этому сервису исходящий адрес интерфейса.
- Учитываются только активные подключения NetworkManager типа `vpn` из `/etc/vpnctl.json`.
- Нет фильтра по профилю и нет интервала между двумя датами.
- `--changes` не смотрит текст `detail` и не сравнивает строку с тем, что было до начала окна `--days`.
- База содержит UUID, адреса серверов и наблюдаемые внешние IP. Каталог `700`, файл `600`, владелец root. В Git её не коммитят.
- Перед переустановкой системы файл нужно скопировать отдельно. Установщик и `git pull` историю не восстанавливают.
