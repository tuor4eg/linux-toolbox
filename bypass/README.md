# bypass

`bypass` добавляет исключения из системной VPN-маршрутизации: выбранные IPv4-адреса и подсети идут через обычный шлюз, а не через туннель Outline/Hiddify.

Утилита в репозитории ведёт реестр маршрутов и правил, которые создала сама (`/var/lib/bypass/managed-routes.json`). Чужой или оставшийся от старой версии маршрут она не захватывает и не удаляет. Отдельной команды миграции нет.

Общая установка: [INSTALLATION.md](../INSTALLATION.md). Восстановление компьютера: [docs/recovery.md](../docs/recovery.md). Остальные утилиты: [README.md](../README.md).

## Что делает

Для каждого адреса исключения `bypass` делает три вещи:

1. Ставит правило `ip rule` с priority `800` (если в политике не задано другое): `from all to АДРЕС lookup main`.
2. Ставит маршрут этого адреса в таблицу `main` через обычный шлюз и его интерфейс.
3. Ставит такой же маршрут в таблицу Outline. Номер таблицы по умолчанию `7113`, ключ политики называется `outline_table`.

Меньший priority в `ip rule` ядро обрабатывает раньше. Правило с `800` рассчитано на то, что оно срабатывает раньше правил Outline/Hiddify и отправляет адрес в таблицу `main`, где лежит маршрут через физический шлюз. Маршрут в таблице `7113` нужен на случай, если пакет всё же попал в таблицу Outline.

`vpnctl` для рабочих сетей использует priority `810`. Исключение `bypass` для конкретного адреса поэтому перекрывает более широкое правило `vpnctl`. Рабочие подсети и адрес сервера OpenVPN в исключения лучше не добавлять. Для этого есть защищённые сети и адреса в политике.

Команда рассчитана на схему, в которой обычный default остаётся в таблице `main`, а прокси уводит остальной трафик policy routing. Имя интерфейса шлюза — эвристика: не подходят интерфейсы, чьё имя начинается с `tun`, `tap`, `wg`, `ppp`, `outline`, `docker`, `br-`, `veth`, `tailscale` или `zt`.

Трафик, который программа сама отправляет в SOCKS- или HTTP-прокси, эти правила не меняют. Обход любого VPN, fwmark, firewall или NAT утилита не обещает. IPv6 она не обрабатывает.

У `bypass` нет фоновой службы. После смены Wi-Fi или шлюза маршруты нужно обновить командой `sudo bypass restore`.

## Установка

Из корня репозитория. Проверка систему не меняет:

```bash
cd ~/pets/linux-toolbox
./install.sh check bypass
./install.sh install bypass
```

Та же проверка из каталога утилиты: `./install.sh` или `./install.sh --check`. Установка: `./install.sh --install`.

Программа оказывается в `/usr/local/bin/bypass`. Нужны Python 3, `ip` из iproute2 и `sudo`. Политика, список исключений и реестр при установке не создаются.

Если `/usr/local/bin/bypass` уже есть и в файле нет `managed-routes.json`, установка останавливается даже с `--replace`: это старая копия без реестра, автоматической миграции нет. Если строка `managed-routes.json` в файле есть, `./install.sh install bypass --replace` заменяет только программу. Маршруты, политика, исключения и реестр при этом не меняются. Подробности ниже.

## Настройка с нуля

Политика необязательна. Без файла `/etc/bypass-policy.json` используются таблица `7113`, priority `800` и пустые списки защиты. Пустая защита по-прежнему отвергает loopback, multicast, адрес `0.0.0.0/32` и IPv4 из аргумента `--remote` у уже запущенных процессов OpenVPN. Корпоративные подсети сами в этот список не попадают: их нужно записать локально, если их нельзя отправлять мимо VPN.

Файл политики можно скопировать из примера и поправить:

```bash
sudo install -m 600 -o root -g root \
  bypass/policy.example.json /etc/bypass-policy.json
sudoedit /etc/bypass-policy.json
```

Пример [policy.example.json](policy.example.json):

```json
{
  "outline_table": 7113,
  "priority": 800,
  "protected_networks": ["10.20.0.0/16"],
  "protected_endpoints": ["198.51.100.10"]
}
```

Допустимы только эти четыре ключа. Любой другой ключ вызывает `Неизвестные параметры политики`. Все ключи можно опустить.

| Ключ | По умолчанию | Смысл |
| --- | --- | --- |
| `outline_table` | `7113` | Номер таблицы, куда дополнительно кладётся прямой маршрут. Целое от 1 до 4294967295. |
| `priority` | `800` | Priority правила `lookup main`. Целое от 1 до 32765. |
| `protected_networks` | пустой список | Сети IPv4. Исключение, которое пересекается с любой из них, отклоняется. |
| `protected_endpoints` | пустой список | Отдельные IPv4. Их нельзя включить в исключение даже более широкой подсетью. |

`10.20.0.0/16` в примере запрещает и сам этот префикс, и любой более широкий префикс, который его перекрывает, например `10.0.0.0/8`, и любой адрес внутри, например `10.20.1.2/32`.

Адрес сервера рабочего OpenVPN имеет смысл держать в `protected_endpoints`. Пока процесс OpenVPN не запущен или адрес сервера записан в его конфиге именем, а не аргументом `--remote`, автоматическая защита этого адреса не срабатывает. Иначе `bypass` может построить прямой маршрут и помешать `vpnctl`, который как раз ведёт этот сервер через Outline/Hiddify.

Пока исключения уже созданы, номер таблицы и priority лучше не менять. Новый priority команда отвергает текстом `изменился приоритет; требуется ручная миграция` и останавливается до записи маршрутов. Новый номер таблицы добавляет маршрут в новую таблицу и не снимает маршрут в старой. Чтобы сменить таблицу или priority, удалите исключения, измените политику и добавьте исключения снова.

Hiddify в `vpnctl` опознаётся по таблице `2022`. `bypass` в эту таблицу маршрут сам не кладёт, пока `outline_table` не указывает на неё. Обход при Hiddify держится на правиле `lookup main` с priority `800`. Если локальные правила Hiddify обрабатываются раньше этого priority, исключение не сработает. Это видно по `ip -4 rule show` и `ip -4 route get АДРЕС`.

Список исключений вручную создавать не нужно: первая успешная команда `add` запишет `/etc/bypass-routes.json`.

## Команды

Общий вид: `bypass {list|add|del|restore}`. Других подкоманд нет. Справки: `bypass -h`, `bypass add -h`.

`list` не проверяет права и ничего не меняет. Файл исключений создаётся с правами `600` и владельцем root, поэтому на практике смотреть его нужно через `sudo`. Если файла ещё нет, `bypass list` молча завершается с кодом 0.

`add`, `del` и `restore` требуют root. Без него сообщение: `Для изменений требуется sudo`. Эти три команды заново применяют все оставшиеся исключения к текущему шлюзу. `restore` дополнительно заново спрашивает DNS для имён.

| Команда | Аргументы | Что делает |
| --- | --- | --- |
| `bypass list` | нет | Печатает сохранённые исключения. Не показывает, лежат ли маршруты в ядре. |
| `sudo bypass add` | одно или несколько имён, IP или префиксов | Резолвит цели, проверяет защиту, записывает их и строит маршруты. Повторный `add` того же имени заменяет его список адресов. |
| `sudo bypass del` | одно или несколько имён в том виде, в каком они сохранены | Убирает имена из файла. Маршрут адреса снимается, только если этот адрес больше не нужен ни одному имени и записан в реестре. Неизвестное имя не считается ошибкой. |
| `sudo bypass restore` | нет | Заново резолвит все имена, проверяет защиту и приводит маршруты к текущему шлюзу. |

Успех `add`, `del` и `restore` заканчивается строкой `OK: add`, `OK: del` или `OK: restore`. Ошибки пишутся в stderr как `Ошибка: ...` и дают код 1.

Что принимается как цель `add`:

- IPv4-адрес. В файле он хранится как сеть `/32`: `203.0.113.10` становится `203.0.113.10/32`.
- Префикс IPv4. Лишние биты хоста отбрасываются: `192.0.2.5/24` сохраняется как `192.0.2.0/24`.
- Доменное имя. Берётся hostname, приводится к нижнему регистру. `https://example.com/path` сохраняется как `example.com`. Запрашиваются только A-записи, каждая кладётся как `/32`.
- Несколько целей в одной команде.

IPv6, пустое имя и адрес без hostname отклоняются (`Некорректный адрес` или ошибка DNS). Имя только с AAAA-записью не резолвится в IPv4, команда `add` завершается ошибкой и файл не переписывает.

Отклоняются также сети loopback (`127.0.0.0/8` и любой более узкий префикс внутри неё), multicast и единственный адрес `0.0.0.0/32`. Более широкий префикс `0.0.0.0/8`, адрес `0.0.0.1/32`, link-local и `255.255.255.255/32` этой проверкой не отсекаются. Отдельно отклоняются пересечение с `protected_networks` (`защищённая подсеть`) и попадание защищённого или живого OpenVPN-сервера внутрь запрошенной сети (`адрес VPN-сервера`). Частные адреса сами по себе разрешены, если они не перечислены в политике.

Один и тот же IP можно сохранить под двумя именами. Маршрут один. `del` первого имени оставляет маршрут, пока второе имя на него ссылается.

`list` печатает имена по алфавиту и под каждым сохранённые адреса:

```text
example.com
  → 203.0.113.10/32
```

Файл после успешной команды переписывается целиком, ключи сортируются. Это объект «имя → список строк IPv4/CIDR»:

```json
{
  "203.0.113.0/24": [
    "203.0.113.0/24"
  ],
  "example.com": [
    "203.0.113.10/32",
    "203.0.113.11/32"
  ]
}
```

## Примеры

Диагностика перед изменениями. Эти команды маршруты не трогают:

```bash
ip -j -4 route show table main default
ip -4 rule show
ip -4 route show table main
ip -4 route show table 7113
sudo bypass list
sudo cat /etc/bypass-policy.json
sudo cat /var/lib/bypass/managed-routes.json
```

Если в политике другой `outline_table`, в последней команде `route show` подставьте его вместо `7113`.

Добавление домена, адреса и подсети. Это уже меняет маршруты:

```bash
sudo bypass add example.com
sudo bypass add 203.0.113.10
sudo bypass add 203.0.113.0/24
sudo bypass add example.net 203.0.113.20
```

Просмотр, удаление одного исключения и обновление DNS вместе со шлюзом:

```bash
sudo bypass list
sudo bypass del example.net
sudo bypass restore
```

После смены Wi-Fi достаточно `sudo bypass restore`. Команда заново выбирает default в `main` и переписывает только те маршруты, которые есть в реестре. Имена, для которых DNS в этот момент недоступен, остаются со старыми адресами. На stderr будет `DNS недоступен: имя, старые адреса сохранены`, общий результат при этом может быть `OK: restore`.

Автоматический выбор шлюза смотрит IPv4 default-маршруты таблицы `main`. Если их несколько, берётся маршрут с наименьшей `metric`. Если таких маршрутов с одинаковой metric больше одного, команда останавливается: `Неоднозначный default-маршрут в main`. Если default нет: `В main нет маршрута по умолчанию`. Если у выбранного маршрута нет gateway или интерфейс похож на туннель: `Обычный физический шлюз не определён`. Эти ошибки происходят до записи исключений и до изменения маршрутов.

Одновременные `add`, `del` и `restore` ждут друг друга на блокировке `/run/lock/bypass.lock`. `list` блокировку не берёт.

### Outline и Hiddify

Включите системный режим Outline или Hiddify, в котором появляется policy routing, а в `main` остаётся обычный default через Wi-Fi или Ethernet. Затем добавьте исключение и проверьте, что `ip -4 route get 203.0.113.10` показывает физический интерфейс и шлюз, а не `tun` или `outline`.

Прокси, указанный только в настройках браузера, эта проверка не покрывает: браузер может продолжать ходить через SOCKS, хотя `ip route get` уже показывает прямой маршрут.

Таблица Hiddify `2022` описана выше. Менять `outline_table` на `2022` стоит только если вы сознательно хотите прямой маршрут ещё и внутри таблицы Hiddify и готовы перед этим удалить старые исключения.

### Реестр владения

Реестр появляется после первого успешного изменения. Версия файла — `1`. Ключ маршрута имеет вид `ТАБЛИЦА|АДРЕС`, значение правила — priority строкой, потому что так его записывает программа:

```json
{
  "routes": {
    "7113|203.0.113.10/32": {
      "dev": "wlan0",
      "gateway": "192.0.2.1"
    },
    "main|203.0.113.10/32": {
      "dev": "wlan0",
      "gateway": "192.0.2.1"
    }
  },
  "rules": {
    "203.0.113.10/32": "800"
  },
  "version": 1
}
```

Своим правилом считается только строка вида `800: from all to 203.0.113.10/32 lookup main`, без fwmark и других селекторов. Правило с другим видом утилита не признаёт своим. Если такое же правило уже есть, а в реестре его нет, команда останавливается: `существующее неучтённое правило` или `чужое/унаследованное правило`. Существующий маршрут с тем же адресом тоже не перехватывается: `чужой/унаследованный маршрут; автоматический захват запрещён`.

Если маршрут из реестра кто-то изменил (другой gateway или интерфейс), удаление этого адреса останавливается: `маршрут изменён извне; удалять нельзя`. Чужое правило, которого нет в реестре, `del` не удаляет.

Локальная сеть Docker — отдельный случай. Если в `main` уже есть маршрут без gateway через `docker0` или интерфейс `br-...`, дополнительный маршрут через физический шлюз не создаётся. Правило `lookup main` для этого адреса всё равно ставится.

Ошибка посреди применения может оставить часть маршрутов уже обновлённой: каждый свой маршрут записывается в реестр сразу после команды `ip`. Если строки `OK:` не было, смотрите `ip -4 route`, `ip -4 rule` и реестр. Автоматического отката нет.

Удаление файла реестра при ещё живых маршрутах оставляет их без владельца. Следующий `add` или `restore` увидит их как чужие и остановится, не удалив. Сначала снимите исключения командой `del` или `restore` на пустом списке, и только потом убирайте реестр.

## Файлы

| Путь | Права | Содержание |
| --- | --- | --- |
| `/usr/local/bin/bypass` | `755`, root | Программа. |
| `/etc/bypass-routes.json` | `600`, root | Исключения. В Git не класть. |
| `/etc/bypass-policy.json` | как выставите при копировании; разумно `600` | Необязательная политика. В Git не класть. |
| `/var/lib/bypass/managed-routes.json` | `600`, root | Реестр своих маршрутов и правил. В Git не класть. |
| `/run/lock/bypass.lock` | создаётся при изменении | Блокировка. После перезагрузки каталог `/run` пуст, это нормально. |

Каталог `/var/lib/bypass` создаётся с обычной маской root, отдельно в `700` он не переводится. Недоступен для чтения именно файл реестра.

Номера версии у программы нет. Признак этой версии в установленном файле — строка `managed-routes.json`:

```bash
grep -F 'managed-routes.json' /usr/local/bin/bypass
```

## Права и sudo

`sudo` нужен для `add`, `del`, `restore` и практически для `list`, потому что конфиг имеет режим `600`.

Чтение `/proc` у процессов OpenVPN выполняется при изменении исключений, чтобы не построить прямой маршрут на их `--remote`. Читается только командная строка. Файлы конфигурации OpenVPN, ключи и пароли утилита не открывает. Если `--remote` нет в командной строке, а сервер указан лишь внутри конфига, этот адрес автоматически не защищается.

## Проверка

Тесты из репозитория подменяют системные команды и реальные маршруты не меняют:

```bash
cd ~/pets/linux-toolbox
python3 bypass/test_bypass_v2.py
```

Проверка живого исключения. `add` меняет маршруты; следующие команды только смотрят результат. Адрес замените на тот, который только что добавили.

```bash
sudo bypass add 203.0.113.10
sudo bypass list
ip -4 rule show
ip -4 route get 203.0.113.10
```

Ожидание: в правилах есть priority `800` на этот адрес с `lookup main`, а `route get` показывает gateway и интерфейс обычной сети, не туннель. В `sudo bypass list` виден `203.0.113.10/32`. В реестре есть ключи `main|203.0.113.10/32` и `7113|203.0.113.10/32`.

`list` сам по себе не доказывает, что маршрут установлен. Сверяйте его с `ip`.

## Обновление

`git pull` обновляет только репозиторий. Установленная программа обновляется отдельно.

Если в `/usr/local/bin/bypass` уже есть строка `managed-routes.json`, это v2. `--replace` меняет только файл программы. Маршруты приводятся в соответствие отдельной командой `restore`, её установщик не вызывает:

```bash
cd ~/pets/linux-toolbox
git pull
./install.sh check bypass
./install.sh install bypass --replace
sudo bypass restore
```

Проверка перед заменой:

```bash
grep -F 'managed-routes.json' /usr/local/bin/bypass
```

Если строки нет, `--replace` завершится отказом и файл не тронет. Снимать старые маршруты и ставить программу заново нужно по разделу миграции ниже. Удалять `/usr/local/bin/bypass` у v2, чтобы поставить файл без `--replace`, не требуется.

## Отключение и удаление

Сначала снимите свои исключения, пока программа ещё на месте. Это меняет маршруты.

```bash
sudo bypass list
sudo bypass del example.com 203.0.113.10/32 203.0.113.0/24
```

Имена в `del` должны совпадать с ключами из `list`. После этого снова посмотрите правила и маршруты. Своих строк priority `800` и записей реестра для этих адресов больше быть не должно.

Снять всё сразу можно так: сохранить копию `/etc/bypass-routes.json` в безопасное место, удалить файл исключений и выполнить `restore`. Пустой список означает «своих адресов больше не нужно», и команда снимет объекты из реестра, затем запишет пустой объект `{}`.

```bash
sudo cp -a /etc/bypass-routes.json /root/bypass-routes.json.bak
sudo rm /etc/bypass-routes.json
sudo bypass restore
```

Если маршрут меняли снаружи, такая очистка остановится на `маршрут изменён извне` и часть адресов может уже быть снята. Тогда разберите оставшиеся строки по реестру и `ip -4 rule show` вручную.

Когда своих правил и маршрутов не осталось:

```bash
sudo rm -f /usr/local/bin/bypass
sudo rm -f /etc/bypass-routes.json /etc/bypass-policy.json
sudo rm -f /var/lib/bypass/managed-routes.json
sudo rmdir /var/lib/bypass
```

Последние три файла удаляйте, только если история исключений больше не нужна. Для переустановки системы их как раз надо сохранить заранее, см. [docs/recovery.md](../docs/recovery.md).

## Ошибки и диагностика

| Что видно | Что проверить |
| --- | --- |
| `Permission denied` на `bypass list` | Смотрите через `sudo`. Файл имеет режим `600`. |
| `Для изменений требуется sudo` | Повторите `add`, `del` или `restore` через `sudo`. |
| `В main нет маршрута по умолчанию` | Есть ли IPv4 default в таблице `main`: `ip -4 route show table main default`. |
| `Неоднозначный default-маршрут в main` | Два default с одной и той же metric. Оставьте один основной маршрут и повторите. Система этой ошибкой не изменена. |
| `Обычный физический шлюз не определён` | Default смотрит в туннель или у него нет gateway. `bypass` в этот момент маршруты не меняет. |
| `защищённая подсеть` или `адрес VPN-сервера` | Адрес пересекается с политикой или с `--remote` живого OpenVPN. Для рабочей сети это ожидаемый отказ. |
| `чужой/унаследованный маршрут` или `существующее неучтённое правило` | Маршрут или правило уже есть, а реестр его не содержит. Частый след старой версии. Новая команда ничего не заменила. Ниже раздел про миграцию. |
| `маршрут изменён извне; удалять нельзя` | В ядре другой gateway или интерфейс, чем в реестре. Утилита его не трогает. Сверьте `ip -4 route` и реестр. |
| `Некорректный реестр собственных маршрутов` | Файл реестра повреждён или в нём не `version: 1`. Не удаляйте его, пока в ядре лежат маршруты этой утилиты: без реестра они станут чужими. |
| `DNS недоступен: ... старые адреса сохранены` | Имя не резолвится во время `restore`. Старые IP этого имени остаются, остальные исключения обрабатываются дальше. |
| Нет строки `OK:`, при этом часть адресов уже на новом шлюзе | Сбой посреди применения. Сверьте реестр и `ip route`. Повторять команду можно после устранения причины: свои целые записи команда догонит. |

Полезный набор, который ничего не меняет:

```bash
sudo bypass list
ip -j -4 route show table main default
ip -4 rule show
ip -4 route get 203.0.113.10
sudo cat /var/lib/bypass/managed-routes.json
```

## Ограничения и безопасность

- Только IPv4 и только системные маршруты и правила. Прокси внутри приложения остаётся при нём.
- Выбор «физического» шлюза основан на default в `main`, metric и имени интерфейса. Необычное имя виртуального интерфейса может быть принято за обычный шлюз.
- Нет демона. Смена сети сама маршруты исключений не обновляет.
- Нет захвата старых объектов. Это сделано намеренно.
- Распознаётся узкий формат правила `from all to АДРЕС lookup main`. Правило с дополнительными условиями не считается тем же самым.
- Защита серверов OpenVPN видит только IPv4 в аргументе `--remote` командной строки процесса, путь которого заканчивается на `/openvpn`. Имя в `--remote` и адрес, записанный только в конфиге, пропускаются.
- Пустая политика не защищает ваши рабочие сети.
- Конфиги содержат список адресов, которые ходят в обход VPN. Их права — `600`. В репозиторий их не копируют.
- Смена `outline_table` при живых исключениях оставляет маршрут в прежней таблице. Смена `priority` отвергается, пока старые правила есть в реестре.
- Одновременная правка одних и тех же адресов через `bypass` и `vpnctl` не согласуется общим замком. Не добавляйте в `bypass` адрес сервера OpenVPN и сети из `expected_networks` профиля `vpnctl`.

### Миграция со старой версии

Старая версия, которой в этом репозитории уже нет, создавала маршруты и правила, не записывая их в реестр. Текущая версия считает такой объект чужим. Поэтому замена одного исполняемого файла на другой не является обновлением.

Что происходит, если всё же записать новый файл поверх старого и вызвать `restore` или `add` для тех же адресов:

1. В ядре ещё лежат старые маршрут и правило.
2. Реестра на них нет.
3. Команда останавливается с `чужой/унаследованный маршрут` или `существующее неучтённое правило`.
4. Файл исключений и ядро остаются как были, если остановка случилась на предварительной проверке.
5. `del` новой версии снимает только то, что записано в реестре. Старые объекты после такой замены продолжают жить, а новая программа отказывается вести те же адреса.

Установщик повторяет запрет миграции: `--replace` не подменяет файл, в котором нет `managed-routes.json`, и не снимает старые маршруты. Ручная замена такого файла копированием тоже не является миграцией. Для уже установленной v2 `--replace` разрешён и меняет только программу.

Исходников старой версии в репозитории нет, поэтому точный текст её команд здесь не приводится. Пока старый файл ещё установлен, снимите исключения его собственным способом и убедитесь диагностикой, что соответствующих строк больше нет в `ip -4 rule show`, `ip -4 route show table main` и `ip -4 route show table 7113`. Сохраните копию `/etc/bypass-routes.json` вне Git.

После этого удалите старую программу и поставьте эту:

```bash
sudo rm /usr/local/bin/bypass
cd ~/pets/linux-toolbox
./install.sh install bypass
sudo install -m 600 -o root -g root bypass/policy.example.json /etc/bypass-policy.json
sudoedit /etc/bypass-policy.json
sudo bypass add example.com
```

Если файл исключений уже в виде объекта «имя → список IPv4/CIDR», его можно оставить и вместо серии `add` выполнить `sudo bypass restore`. Если формат старого файла другой, `restore` сообщит об ошибке JSON или `Некорректная запись исключений` и маршруты не запишет. Тогда оставьте копию старого файла в стороне и наберите исключения заново через `add`.

Если новая программа уже стоит, а старые маршруты остались, она их не вычистит. Удалять их командами `ip` можно только после того, как вы по выводу `ip -4 rule show` и `ip -4 route show` узнали свои прежние исключения. Чужое правило с тем же priority трогать нельзя. Команды ниже меняют маршрутизацию; адреса и интерфейс замените на свои, это лишь форма вызова:

```bash
sudo ip -4 rule del priority 800 to 203.0.113.10/32 lookup main
sudo ip -4 route del 203.0.113.10/32 via 192.0.2.1 dev wlan0 table main
sudo ip -4 route del 203.0.113.10/32 via 192.0.2.1 dev wlan0 table 7113
```

Когда этих строк больше нет, `sudo bypass add` или `sudo bypass restore` создаёт новые объекты и записывает реестр. С этого момента удаление и смена шлюза идут через `bypass`, а не через ручной `ip`.
